Level instructions and case study — Manager and Senior Manager, Platform/DevOps Engineering 
This exercise evaluates DevOps and cloud/infrastructure engineering skill using a generative-AI 
application as the workload. It intentionally keeps the AI/model logic simple so your time and our 
evaluation stay focused on build, deployment, and operability — the skills the role is actually hiring for.

Senior Manager Platform/DevOps Engineer 
A note on AI usage: Using AI assistants (coding assistants, chat tools, etc.) for this exercise is allowed 
and encouraged. We want to see how you actually work, and that includes how effectively you use the 
tools available to you. The only requirement is transparency — please be ready to clearly disclose to the 
interviewers which parts of your solution were AI-assisted and how you used it. 
At the Senior Manager level, we expect a solution that demonstrates strong hands-on platform 
engineering capability combined with product-minded software delivery. You should focus on building a 
robust, maintainable, and production-ready solution that reflects how you would deliver build and 
infrastructure capabilities for an AI-powered product in a real environment. 
We expect you to approach the case not only as a build or provisioning exercise, but as an end-to-end 
engineering problem: from pipeline and infrastructure design to deployment strategy, operability, and 
clear technical communication. Your solution should show sound engineering judgment, practical trade-
off decisions, and strong attention to reliability, cost, and operational quality specific to running a 
generative-AI workload. 
In addition to technical depth, we are looking for evidence that you can work effectively in a cross-
functional product setting, balancing speed, reliability, security, and maintainability. We also value how 
you structure your work so it can be extended by others, including through clear documentation, 
modular design, and good engineering practices. 
What we mean by “AI application” in this exercise 
The workload is a generative-AI service — typically a retrieval-augmented generation (RAG) API or 
chatbot backend — not a model-training pipeline. You are not being asked to train a model. 
Use a managed foundation model (Amazon Bedrock is the easiest path — no GPU quota requests, 
pay-per-token) rather than self-hosting an LLM, unless you specifically want to showcase 
GPU/inference infrastructure, in which case a small open-weight model on SageMaker or Fargate is 
a reasonable “extra credit” alternative. 
A realistic AI service for this exercise has three moving parts you can reason about independently: 
an ingestion/indexing job (turns a small document set into embeddings), a vector store 
(OpenSearch Serverless, Aurora pgvector, or similar), and an inference API (retrieves context, calls 
the model, returns an answer). Treat each as a component with its own build, deploy, and rollback 
story.

Case 1: CI/CD Pipeline for a GenAI RAG Microservice on AWS (Build & Release) 
Objective: 
Design and implement a CI/CD pipeline that builds, tests, and deploys a small retrieval-augmented 
generation (RAG) service to AWS: an ingestion job that embeds a small document set, and an inference 
API that answers questions using that index and a foundation model. Use one of the reference repos 
above as a starting point or scope reference — feel free to strip it down to 2–3 components rather than 
the full solution. 
Task: 
Build a pipeline that automates linting, testing, building container images, and deploying your chosen 
components to AWS using a simple, lightweight setup (e.g., ECS or App Runner). Apply appropriate 
practices for versioning, artifact management, and promoting a build across at least two environments. 
In addition to pipeline mechanics, show how you would structure the solution for production use, 
including a deployment strategy (e.g., blue-green or canary) for the inference API, a rollback approach 
for both the service and the vector index, and basic release monitoring or gating — for example, a 
response-quality or latency check gating promotion to production. 
Case 2: Infrastructure as Code for a GenAI/RAG Platform on AWS (Infra/DevOps) 
Objective: 
Provision the AWS infrastructure needed to run a small GenAI RAG service across two or more 
environments: a vector store, a foundation model access path, and the compute/networking for the 
inference API. Keep the footprint simple: a basic networking setup, a compute layer, and a managed 
vector store are sufficient. 
Task: 
Write Infrastructure as Code to provision the environments in a reproducible, parameterized way. The 
choice of IaC tool is entirely up to you (e.g., Terraform, AWS CDK, CloudFormation, or Pulumi). Handle 
secrets and model/API access cleanly, structure the code into reusable modules, and evaluate your 
design using criteria such as repeatability and blast-radius containment. In addition to provisioning, 
demonstrate how you would operate the environment in practice, including basic monitoring/alerting

Appendix: guidance, scope, and common pitfalls 
This section applies to both levels and both cases. It exists to help you spend your limited time on the 
things we actually evaluate. 
What “good” looks like at a glance 
• A pipeline or IaC module set that actually runs, even if the AI logic behind it is intentionally simple. 
• Clear reasoning for trade-offs (managed vs. self-hosted model, vector store choice, blast-radius 
containment) rather than defaulting to the fanciest option. 
• Evidence you thought about the AI-specific failure modes: a bad or slow model response, a stale 
index, a runaway cost from an unthrottled endpoint — not just generic infra failure modes. 
Common pitfalls to avoid 
• Spending most of the week on the AI/model logic and leaving little time for the pipeline or IaC 
quality — remember the AI service is the workload, not the subject of evaluation. 
• Deploying the full reference repo unmodified — we want to see your own structuring and judgment 
on a smaller slice, not a fork with your name on it. 
• Skipping the second environment or the rollback story — these are explicitly scored and easy to 
shortchange under time pressure.
